# Windows 固定宽度任务行设计

## 目标

保持监视面板 330 DIP 的固定宽度。每一行的任务标题只能使用“状态点”和“已处理”按钮之间的剩余空间；标题过长时在单行内显示省略号，不能把右侧按钮顶出面板。“已处理”按钮始终固定在同一任务行的最右侧，第二行“状态 · 项目名”保持现状。

## 当前问题

当前任务行已经给标题设置 `TextTrimming="CharacterEllipsis"`，并使用“18 DIP 状态点 / 星号标题列 / Auto 按钮列”的 Grid。但是外层 `ListBox` 没有禁用横向滚动，WPF 的滚动测量过程可以给内容一个不受面板宽度约束的水平尺寸。在这种测量下，标题不会获得有限的可用宽度，省略号无法生效，Auto 宽度的“已处理”按钮可能被长标题推到 330 DIP 面板之外。

问题属于任务行的布局约束，不涉及标题数据、状态计算或按钮行为。

## 方案选择

采用约束式 Grid 方案：

- 禁止任务列表横向滚动，让每个 ListBoxItem 按可见视口宽度测量。
- 保留固定面板宽度和三列结构。
- 明确将标题列设为可收缩的 `*` 列，并将最小宽度设为 0。
- 标题打开按钮也允许水平收缩；标题 TextBlock 保持单行和字符省略。
- “已处理”列继续使用 `Auto`，因此按钮先保留自身所需宽度，标题只使用剩余宽度。

不采用标题固定像素宽度，因为它会把面板边距、字体和按钮文字耦合到一个脆弱常数；也不改用 WrapPanel 或 DockPanel，以免改变第二行元数据和整行点击区域。

## 布局规则

任务行仍为 62 DIP 内容高度、左右 14 DIP 边距：

```text
┌─ 330 DIP 固定面板 ──────────────────────────────┐
│  ●  很长的任务标题，超过剩余宽度后显…  [已处理] │
│     等待处理 · 项目名                           │
└─────────────────────────────────────────────────┘
```

具体规则：

1. `ListBox` 的水平滚动必须为 `Disabled`，垂直滚动继续为 `Auto`。
2. 行内状态点列保持 18 DIP。
3. 标题列使用剩余宽度，`MinWidth=0`，不得用内容的自然宽度扩大任务行。
4. 标题保持 `TextWrapping=NoWrap` 与 `TextTrimming=CharacterEllipsis`。
5. “已处理”按钮列保持 `Auto`，按钮必须完整位于任务行右边界以内。
6. 等待处理任务显示按钮；运行中任务继续折叠按钮，标题可以使用释放出的空间。
7. 点击标题区域仍执行打开任务；点击“已处理”仍只执行已处理操作，两个点击区域不重叠。

## 测试设计

使用现有 STA WPF 测试结构增加真实布局回归：

1. 从 `MainWindow.TaskList.ItemTemplate` 创建等待处理任务行，标题使用足够长的合成文本。
2. 以 330 × 63 DIP 测量并排列整行，等待数据绑定和布局完成。
3. 断言任务列表横向滚动为 `Disabled`。
4. 断言标题 TextBlock 使用单行字符省略。
5. 将标题和“已处理”按钮坐标转换到任务行坐标系，断言标题右边界不超过按钮左边界，按钮右边界不超过任务行右边界。
6. 断言按钮仍为可见且有正宽度，防止通过隐藏或裁掉按钮让测试误通过。
7. 保留现有只读绑定、标题栏拖动、窗口尺寸和完整 Release 回归测试。

测试必须先在当前 XAML 上失败，证明它确实覆盖按钮被推出固定面板的问题；随后只修改布局属性使其通过。

## 范围边界

- 不改变面板 330 DIP 宽度、行高、最多 6 行或垂直滚动行为。
- 不改变标题、状态、项目名的内容或字号。
- 不改变打开任务和“已处理”的命令、身份键或持久化。
- 不改变任务筛选、Fork 处理、rollout 解析、日志或侧栏自动化。
- 不修改 Swift/macOS。
- 不把真实任务标题写入测试、日志或验收证据。

## 验收标准

- 任意长度标题都不能把“已处理”按钮推出 330 DIP 面板。
- 超长标题在按钮之前以省略号结束。
- “已处理”按钮始终完整可见并可点击。
- 第二行状态与项目名、运行中任务布局和现有交互保持不变。
- WPF 聚焦测试、完整 Release 测试和 warnings-as-errors 构建通过。
