# Windows Bark 任务通知设计

## 目标

为 Codex Task Monitor 的 Windows 11 版本增加可选的 Bark 推送。当 Codex 任务正常完成或中止时，监视器向用户的 iPhone 发送一次通知，同时保持现有本地任务扫描、面板交互和错误降级行为不受影响。

通知内容采用以下固定格式：

- 正常完成：Bark 标题为 Codex 任务标题，正文为项目名。
- 中止：Bark 标题为 Codex 任务标题，正文为 `项目名 · 已中止`。
- 通知分组固定为 `Codex Task Monitor`。

本功能只面向 Windows 11 实现，不修改 macOS 版本。

## 用户体验

在主窗口右上角 `•••` 菜单中增加“Bark 设置”。设置窗口包含：

- “启用 Bark 通知”开关；
- 推送地址输入框；
- “发送测试通知”按钮；
- 保存与取消按钮；
- 不包含敏感内容的连接或校验结果。

用户可以直接粘贴 Bark iOS 客户端卡片复制出来的完整示例 URL。程序负责识别 Bark 服务端点和设备密钥，并忽略 `/Body Text`、`/Title/Body Text` 等示例通知内容。输入框不得在设置窗口再次打开时显示完整密钥；可以显示经过遮罩的地址，并通过显式替换操作录入新地址。

“发送测试通知”使用标题 `Codex Task Monitor`、正文 `Bark 连接成功`。测试成功只证明当前地址能够接受请求，不改变任务通知的启用时间、已通知集合或待重试状态。

首次启用 Bark 时记录启用边界。启用时已经存在的绿色“等待处理”任务不补发；只有在启用边界之后新完成或新中止的任务才允许推送。禁用后重新启用会建立新的边界，同样不补发当时已有的任务。

## 方案选择

采用应用内设置和内置 HTTP 客户端，不要求用户手改 `settings.json`，也不调用外部 PowerShell、`curl` 或脚本。

选择该方案的理由：

- 能在保存前校验地址并直接测试；
- 可以用 Windows 当前用户的数据保护能力保存密钥；
- 不受脚本路径、执行策略和命令行转义影响；
- 打包安装后的行为稳定，用户更换 Bark 地址时无需编辑文件。

## 组件边界

### Bark 配置

`BarkSettings` 表示非敏感开关、加密后的连接信息引用、启用时间边界和通知处理记录。现有偏好存储仍负责窗口位置、登录启动、监视基线和已处理任务；Bark 的秘密材料通过单独的保护存储读写，避免领域偏好对象传播明文密钥。

配置能力需要提供以下独立操作：

- 解析并校验用户粘贴的 URL；
- 保存或替换受保护的 Bark 端点；
- 读取遮罩后的显示值；
- 禁用 Bark 而不泄露或记录端点；
- 明确删除 Bark 配置。

### BarkNotificationClient

`BarkNotificationClient` 只负责向配置的 Bark 端点发送 HTTPS POST。请求使用 JSON 负载，并至少包含 `title`、`body` 和 `group`。客户端负责超时、HTTP 状态与 Bark 响应成功状态校验，但不负责判断某个任务是否应该发送。

所有异常必须转换为不含 URL、设备密钥、任务标题和项目名的类别化错误。HTTP 请求、响应正文和授权端点不得写入本地诊断日志。

### TaskCompletionNotifier

`TaskCompletionNotifier` 消费已提交到当前刷新 generation 的监视结果，判断新的终态任务并串行调度推送。它负责：

- 应用启用时间边界；
- 使用精确的 `threadID:turnID` 身份去重；
- 生成正常完成或中止负载；
- 记录成功通知；
- 对暂时失败的通知执行有上限的退避；
- 当任务从监视列表消失或被“已处理”时取消待重试发送。

通知调度不能阻塞任务列表提交。较旧或已取消的刷新 generation 不得产生通知。

### 监视领域模型

现有 `TaskState.Waiting` 同时表示 `task_complete` 和 `turn_aborted`，不足以构造不同的通知正文。`MonitorItem` 因此需要携带独立的终态原因，例如“正常完成”“中止”或“无终态”。面板仍把两种终态显示为现有绿色等待处理状态，不增加新的任务行视觉状态。

终态原因来自已经解析出的 `LifecycleKind`，不重新读取 rollout，也不把通知逻辑放入 `RolloutParser` 或 `TaskStateResolver`。

## 数据流

1. `TaskMonitor` 按现有周期只读扫描 Codex SQLite 和 rollout 文件。
2. `TaskStateResolver` 保留现有运行中、等待处理、基线与已处理过滤语义。
3. `TaskMonitor` 将终态原因连同 `MonitorItem` 返回。
4. `MonitorViewModel` 只在当前刷新 generation 成功提交后，把本次监视结果交给 `TaskCompletionNotifier`。
5. 通知器过滤禁用状态、启用前终态、已经成功通知的身份以及已经离开监视列表的待重试任务。
6. `BarkNotificationClient` 发送 HTTPS POST。
7. 成功后持久化精确任务身份；失败后登记退避状态并让面板显示非阻塞警告。

通知发送失败不改变任务的显示、排序、打开或“已处理”行为。

## 地址解析与校验

输入必须是绝对 HTTPS URL，并包含 Bark 设备密钥所在的路径段。解析器接受 Bark 客户端复制出的正文、标题加正文等示例 URL，但保存前将示例负载从端点中剥离。设计不通过字符串拼接推断 URI，也不允许用户名、密码、片段标识或非 HTTPS scheme。

默认云端 `https://api.day.app/` 必须可用。实现可以兼容具有相同接口的 HTTPS 自托管 Bark 服务，但本次不增加自托管服务器管理、证书例外或 HTTP 明文传输选项。

保存后的端点使用 Windows DPAPI 的当前用户作用域保护。配置文件或秘密文件中只能出现密文；复制到另一 Windows 账户或机器后不能解密。解密失败应视为配置不可用，提示用户重新粘贴地址，不能回退到明文。

## 去重、重启与时间边界

通知身份固定为现有 `MonitorItem.Id`，即 `threadID:turnID`。任务标题、项目名或活动时间不能作为去重键。

启用时间使用 `TimeProvider` 提供的 UTC 时间，并与终态的 `EventDate` 比较。只有终态时间不早于本次启用边界的任务才有资格发送。保存启用状态时必须先建立边界，再允许通知器观察结果，防止配置窗口关闭与下一次轮询之间补发旧任务。

成功发送的任务身份持久化，因此普通轮询、手动刷新、窗口重新激活和应用重启均不能重复通知。若 Bark 在应用退出期间保持启用，应用重启后可以发送启用边界之后完成且尚未成功通知的任务。

如果 HTTP 请求已经成功、但随后本地“已通知”记录保存失败，系统优先保证不丢通知；极少数情况下重启后可能重复一次。该投递语义应在实现注释和测试命名中明确为至少一次，而不能宣称严格恰好一次。

## 失败处理

- URL 校验失败：不保存新地址，设置窗口就地显示通用原因。
- DPAPI 保护或解密失败：不启用通知，要求用户重新配置。
- DNS、连接、超时、非成功 HTTP 状态或 Bark 拒绝：本地任务监控继续运行。
- 发送失败：按逐步增加的延迟重试，最大重试间隔为 15 分钟，禁止跟随 2 秒扫描频率连续请求。
- 待重试任务被“已处理”或不再出现在监视结果中：取消该任务的重试。
- 地址被替换、Bark 被禁用或应用退出：取消旧端点上的在途和待重试工作。
- 多个任务同时完成：使用有界串行队列发送，避免并发刷新造成重复或突发请求。

面板可以显示“Bark 通知发送失败，将自动重试”，但错误优先级不得覆盖更关键的本地扫描错误或现有用户操作错误。错误文字和诊断只包含错误类别、时间与计数，不包含秘密或任务内容。

## 隐私与安全

未启用 Bark 时，应用继续完全本地运行，不产生 Bark 网络请求。启用后，用户明确选择将以下内容发送到所配置的 Bark 服务，并由其转交 Apple 推送服务：

- 任务标题；
- 项目名；
- 正常完成或中止标记；
- 固定通知分组。

线程 ID、turn ID、工作目录完整路径、提示词、rollout 正文、SQLite 内容和 Codex 认证信息不得进入 Bark 负载。任务身份可以保存在本机去重状态中，但不得进入诊断日志。

真实 Bark URL 属于秘密。README、设计文档、测试夹具、截图、构建输出和版本控制中只能使用明显虚构的示例值。

README 中现有“不上传到外部服务”的表述需要改为条件化说明：默认且未启用 Bark 时不上传；用户启用 Bark 后仅发送上述通知字段。

## 测试策略

### 地址与秘密存储测试

- 接受 Bark 正文、标题加正文等客户端示例 URL，并得到相同端点。
- 拒绝相对 URL、非 HTTPS、无密钥、带凭据、带 fragment 和结构无效的地址。
- DPAPI 当前用户作用域可以完成保存与读取往返。
- 磁盘文件与序列化偏好中不出现测试明文密钥。
- 遮罩显示、替换、禁用和删除不会意外返回完整端点。

### 客户端测试

- 使用假的 `HttpMessageHandler` 验证 POST 方法、JSON 编码、标题、正文和固定分组。
- 正常完成正文仅为项目名；中止正文为 `项目名 · 已中止`。
- 测试通知使用固定内容且不改变任务通知状态。
- 超时、取消、非成功 HTTP 状态和 Bark 失败响应映射为脱敏错误。
- 测试失败输出和诊断事件不包含 URL、密钥、任务标题或项目名。

### 通知协调测试

- 禁用时不发送。
- 首次启用不发送当前已有终态任务。
- 启用后正常完成与中止分别发送一次。
- 同一刷新、连续刷新和手动刷新不重复。
- 成功记录在重启后继续去重。
- 启用期间应用退出，重启后补发符合时间边界且未通知的终态任务。
- 禁用再启用建立新边界，不补发当时旧任务。
- 失败按退避计划重试，最大间隔为 15 分钟。
- “已处理”、配置替换、禁用和退出取消相应重试。
- 过期刷新 generation、并发刷新和取消刷新不发送。

### UI 与回归测试

- `•••` 菜单包含“Bark 设置”。
- 设置窗口保存、取消、遮罩输入、校验失败、测试成功和测试失败状态正确。
- Bark 警告不覆盖更高优先级错误。
- 现有任务扫描、打开、已处理、登录启动、固定宽度任务行和侧栏定位测试继续通过。
- 自动测试不访问真实 Bark 服务，也不包含真实设备密钥。

## 验收标准

1. Windows 11 用户能从 `•••` 菜单打开 Bark 设置，粘贴 Bark iOS 客户端复制的示例 URL 并成功发送测试通知。
2. 设置保存后，磁盘和日志中找不到明文 Bark URL 或设备密钥。
3. 启用时的已有绿色任务不产生通知。
4. 新任务正常完成后，iPhone 收到一次以任务标题为标题、项目名为正文的通知。
5. 新任务中止后，iPhone 收到一次以任务标题为标题、`项目名 · 已中止` 为正文的通知。
6. 手动刷新、2 秒轮询和应用重启不重复发送成功通知。
7. Bark 暂时不可用时，面板任务监控和交互保持可用，通知按退避策略重试。
8. 用户禁用 Bark 后不再产生 Bark 网络请求；重新启用不补发当时已有任务。
9. Release 测试、警告视为错误的构建、Windows 打包验证继续通过。
10. 使用真实 iPhone 完成一次测试通知、一次正常完成通知和一次中止通知的人工验收。

## 非目标

- 不修改 macOS 版本。
- 不增加 Android、邮件、Slack 或其他通知渠道。
- 不自建、部署或管理 Bark Server。
- 不支持 HTTP 明文 Bark 端点或忽略证书错误。
- 不增加通知模板编辑、铃声、时效性级别、重要警告、图标、图片或点击跳转配置。
- 不把 Bark 密钥同步到云端或其他 Windows 用户。
- 不改变任务面板的运行中与等待处理视觉语义。
